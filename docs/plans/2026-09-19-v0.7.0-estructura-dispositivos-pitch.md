# proyecto-loop v0.7.0 — Plan de implementación

> **Para ejecución agéntica:** usar `superpowers:subagent-driven-development` (recomendado)
> o `superpowers:executing-plans` para recorrer este plan tarea por tarea. Los pasos usan
> checkbox (`- [ ]`).

**Goal:** que todo proyecto nacido del loop tenga la misma estructura, que la decisión de
hosting de Supabase quede trazable, que cada tarea se verifique en los cuatro dispositivos
reales, que el diseño en Figma tenga estructura y ofrezca opciones, y que el producto
terminado se pueda presentar con `loop-pitch`.

**Architecture:** no se agregan etapas al ciclo. Las reglas se escriben dentro de las
skills que ya existen (`project-init`, `loop-design`, `plan-architect`, `code-exec`,
`loop-verify`, `project-loop`, `loop-ship`) y se suma una sola skill nueva, `loop-pitch`.
Dos archivos de referencia nuevos concentran lo que hoy cada skill improvisaría:
`templates/estructura/monorepo.md` (el árbol canónico) y `references/ui-patterns.md` (el
catálogo de reglas de UI).

**Tech Stack:** skills en Markdown con frontmatter YAML · plugin distribuido por el
marketplace `proyecto-loop-local` · validador `scripts/verificar-arsenal.py` (Python +
pyyaml vía uv) · Maestro como runner de e2e · HyperFrames para la presentación.

**Spec:** `docs/specs/2026-09-19-estructura-dispositivos-pitch-design.md`

## Global Constraints

- **Idioma de todos los prompts de skills: español.**
- Toda skill es **idempotente y reanudable**: lee `.loop/state.md` y completa el delta.
- Una etapa que otra skill **encadena** nunca lleva `disable-model-invocation: true`. El
  flag es solo para puntos de entrada: `project-loop`, `loop-adopt`, `loop-status`,
  `loop-ship`, y ahora `loop-pitch`.
- El repo es **público**: no commitear nombres internos de repos ni del servidor de deploy.
  Referirse a él como "el servidor interno".
- **Nunca** editar `~/.claude/plugins/cache/<version>/`: se pierde en la próxima
  actualización. El fix va al repo con bump de versión.
- Las skills cargan al inicio de sesión: para probar en la app hace falta resync del
  marketplace + **sesión nueva**.
- Ninguna carpeta del árbol estándar se crea vacía. Estructura fija significa *mismo lugar
  cuando existe*, no *todas siempre*.
- Cada tarea termina en un **commit atómico**.

**Comando de test de todo el plan** (desde la raíz del repo):


````markdown
```

## Por qué cada pieza está donde está

**`packages/core`** es la dirección fija del adaptador de datos que `project-init` cablea
en Tier 1. El dominio importa de `core`; **nunca** llama a Supabase directo. Tener una
única dirección es lo que hace que la regla se pueda verificar en vez de recordar.

**`packages/ui`** es la contraparte en código de `.loop/design-system.md`: tokens y
componentes base. Toda pantalla los reusa; nada de estilos ad-hoc por pantalla.

**`supabase/`** existe siempre que el proyecto tenga backend, con las migraciones
versionadas. **`infra/`** solo aparece si el hosting elegido es self-hosted en el servidor
interno; con Supabase Cloud no hay nada que levantar.

**`e2e/`** guarda los flows de Maestro. Vive en la raíz y no dentro de `apps/mobile`
porque los mismos flows corren contra las dos plataformas.

## Reglas de decisión

- **¿Hay mobile?** Lo pregunta `project-init` siempre, no lo infiere. Si la respuesta es
  sí, `apps/mobile` nace con Expo — no se ofrecen alternativas.
- **¿Web?** Solo si el proyecto la pide. Next.js + TypeScript.
- **Proyecto sin UI (data):** tendría `packages/core`, `supabase/` y nada más.
````

```python
    #    Un principio disfrazado de regla chequeable da falsos verdes en la revisión.
    catalogo = open(CATALOGO).read()
    reglas = re.split(r"^## (UI-\d+)[^\n]*$", catalogo, flags=re.M)[1:]

        encabezado = catalogo[catalogo.index(f"## {nombre}"):].split("\n", 1)[0]

            if parte not in cuerpo:
                errores.append(f"{nombre} no tiene la sección {parte}")
```

- [ ] **Paso 1: Agregar la estructura del archivo**

En `skills/loop-design/SKILL.md`, reemplazar íntegra la sección `## 4. Figma` por:

````markdown
## 4. Figma

**Obligatorio: invocá `figma:figma-use` antes de cualquier escritura en Figma.** No
llames a las herramientas de escritura sin haber cargado esa skill; es la causa de los
fallos difíciles de depurar. Para traducir una pantalla concreta a Figma, apoyate en
`figma:figma-generate-design`.

### 4.1 Un archivo por proyecto, páginas fijas

```
<Proyecto> — Design
├── 00 · Foundations     variables reales de color, tipografía, espaciado, radios, motion
├── 01 · Components      componentes base con sus variantes y estados
├── 02 · Mobile          pantallas mobile (secciones Teléfono y Tablet)
├── 03 · Web             pantallas web
├── 04 · Flows           cómo se encadenan las pantallas
├── 05 · Opciones        variantes a elegir (ver 4.4)
└── 99 · Archive         descartes: no se borran, pero no se implementan
```

El número fija el orden y hace el nombre estable para búsqueda. Las páginas que el
proyecto no usa no se crean. Foundations y Components viven **dentro del archivo del
producto**, no en una librería aparte: cada producto tiene su propia dirección estética.

### 4.2 El nombre del frame es la clave del mapa

Un frame por pantalla **y por estado**:

```
H-03 · Checkout · default
H-03 · Checkout · vacio
H-03 · Checkout · carga
H-03 · Checkout · error
```

`H-03` es el id de historia de `.loop/analysis.md`. Con eso la cadena queda cerrada:
historia → frame → fila en `design.md` → tarea en `plan.md` → componente en `packages/ui`.

**Los ids de historia son inmutables una vez emitidos.** Si una replanificación los
renumera, los frames quedan desalineados con `design.md` y el mapa se rompe en silencio.
Si necesitás historias nuevas, seguí numerando; no reordenes.

### 4.3 Teléfono y tablet, las dos

El gate de verificación corre en tablet Android e iPad en **cada** tarea. Si solo diseñás
teléfono, el layout de tablet lo improvisa la implementación y la matriz lo reporta como
rojo sin una referencia contra la cual arreglarlo: pagás el costo de testear en tablet sin
el beneficio de haber diseñado para tablet.

Por eso **cada pantalla existe en las dos secciones** de `02 · Mobile`.

**Los tamaños de frame se derivan de los dispositivos de la matriz**, no se hardcodean.
````
