# proyecto-loop v0.8.0 — Subproyecto A: el loop en la nube

**Fecha:** 2026-09-24 · **Versión objetivo:** `proyecto-loop` v0.8.0 (desde v0.7.0)

**Goal:** que un proyecto nazca, se construya y se verifique sin depender de que la
máquina de Gabriel esté encendida. El código vive en GitHub y el loop corre en sesiones
cloud de Claude Code.

## Descomposición

El pedido original tiene tres subsistemas que se construyen, prueban y rompen por
separado. Cada uno lleva su propio ciclo de spec, plan e implementación:

| | Qué resuelve | Estado |
|---|---|---|
| **A. Repo en GitHub + loop en sesión cloud** | El código vive en GitHub y el loop corre sin la máquina local | **Este spec** |
| B. Matriz de dispositivos en EAS Workflows | La verificación en dispositivos sale de la máquina local | Pendiente |
| C. Deploy con runner self-hosted de GitHub Actions | `loop-ship` funciona sin que la máquina local alcance la red interna | Pendiente |

A va primero porque B y C dependen de que el repo esté en GitHub. B antes que C porque es
lo de mayor valor y no toca producción.

## Hechos verificados

Todo lo de esta sección se comprobó contra documentación oficial o contra la máquina el
2026-09-23/24. Lo que no se pudo comprobar está en **Supuestos sin verificar**, al final.

**Sesiones cloud** (documentación de Claude Code):

- Corren en una VM gestionada y **siguen corriendo con la máquina local apagada**. No hay
  cargo de cómputo aparte: comparten el límite de uso de la cuenta.
- Se inician desde la app de escritorio (*Cloud* en vez de *Local*), claude.ai/code, la
  app móvil, `claude --cloud` o *routines* programadas.
- Trabajan sobre un clon del repo en GitHub. Necesitan que el código esté pusheado.
- Entorno: **Ubuntu 24.04**, con Node 20-22, OpenJDK 21 con Gradle, Python con `uv`,
  **Docker** y **PostgreSQL 16** preinstalados. Un *setup script* corre como root antes de
  que arranque Claude Code.
- Red: el nivel por defecto (*Trusted*) permite GitHub y los registros de paquetes. **No
  incluye** `expo.dev`, Supabase ni Sentry; para eso hace falta *Custom* o *Full*. Los
  conectores de claude.ai pasan igual, porque viajan por los servidores de Anthropic.

**Qué llega a una sesión cloud y qué no:**

| | ¿Llega? |
|---|---|
| `.claude/skills/`, `.claude/agents/`, `.claude/rules/`, `CLAUDE.md`, `.mcp.json` del repo | **Sí** — son parte del clon |
| Plugins declarados en el `.claude/settings.json` del repo | **No** — la doc lo dice textual |
| `~/.claude/settings.json`, `~/.claude/skills/`, plugins del usuario | **No** — viven en la máquina local |
| Plugins y skills activados en la cuenta de claude.ai ("synced plugins") | Sí, pero **no está documentado** si un plugin de marketplace propio califica |

**Conclusión que manda todo el diseño: tal como está hoy, en una sesión cloud el loop no
existe.**

**Dependencias externas del loop** (relevadas con `grep` sobre `skills/`):

| Grupo | Skills | ¿Se pueden vendorear? |
|---|---|---|
| Propias | `proyecto-loop`, `dev-substrate` | Sí |
| Oficiales | `engineering:*` (6 usos), `design:design-critique` (4), `figma:*` (3) | **No** — las provee la app, no son archivos |
| Terceros | ver tabla de licencias | Según licencia |

## Decisiones

**1. El loop se vendorea en cada repo.** Descartado: *synced plugin* de claude.ai, porque
no está documentado que un plugin de marketplace propio califique; diseñar sobre eso sería
apostar a algo sin confirmar. Vendorear además fija la versión del loop con la que se
construyó cada proyecto.

**2. Los proyectos nacen de un repo plantilla en GitHub.** Resuelve un huevo y gallina: en
una sesión cloud sobre un repo vacío, `project-init` no existe, y es la skill que
vendorearía el loop. La plantilla ya lo trae adentro. Descartado: arranque local una vez,
porque obliga a tener la máquina encendida para cada proyecto nuevo.

**3. El gate de dispositivos se difiere con deuda explícita.** Mientras no exista B, las
tareas de UI no se pueden verificar en dispositivos en la nube. Descartados: *mobile espera
a B* (el full-auto queda a medias) y *bloquear en la nube* (lo apaga para cualquier
proyecto con pantallas).

**4. Se vendorea lo propio más un subconjunto selectivo de terceros.** Entran
`design-taste-frontend` y `react-native-best-practices`: licencia MIT, y el valor justifica
el peso. Queda afuera `hyperframes`: solo la usa `loop-pitch`, que es manual y necesita
`ffmpeg` para renderizar. Las tres sin licencia no se vendorean. Lo que falte se **degrada
explícitamente**. Descartado: vendorear todo lo permitido — no tapa las brechas grandes,
porque las más usadas (`design-critique`, `code-review`) son oficiales y no se pueden
copiar.

**5. Propuestas aceptadas sin objeción:**

- El `.claude/settings.json` de la plantilla **desactiva el plugin global** `proyecto-loop`
  para ese proyecto. Así corre la misma versión —la vendoreada— en la nube y en local.
- La plantilla se regenera **con cada tag `v*`**, no con cada push a `main`: un proyecto
  nuevo nunca nace con un loop a medio hacer.
- `loop-actualizar` baja del repo **público** `proyecto-loop`, no de la plantilla privada.
- Las revisiones que no pudieron correr por skills ausentes **no bloquean la entrega**; se
  listan en el reporte. La diferencia con los dispositivos es deliberada: la matriz
  confirma que la app funciona; la crítica de diseño es juicio.

## Arquitectura

```
proyecto-loop (público, fuente de verdad)
      │  tag v*  →  Action corre scripts/vendorear.py
      ▼
proyecto-loop-plantilla (privado, marcado como template)
      │  "Use this template" — navegador o celular
      ▼
proyecto nuevo (privado)  ──►  sesión cloud  ──►  /project-loop
   └─ .claude/ con el loop adentro
```

### `scripts/vendorear.py` — la única transformación

Un solo script arma el `.claude/` de un proyecto a partir del plugin. Lo usan la Action y
`loop-actualizar`, así la lógica vive en un lugar y se prueba localmente. Hace cinco cosas:

1. Copia las skills de `proyecto-loop` y `dev-substrate` a `.claude/skills/`, y los
   subagentes de `dev-substrate` a `.claude/agents/`.
2. Copia los recursos no ejecutables —plantillas, catálogo de UI, árbol canónico, catálogo
   de reglas— a `.claude/loop/`.
3. **Reescribe `${CLAUDE_PLUGIN_ROOT}/…` a `.claude/loop/…`** (7 apariciones hoy). Esa
   variable solo existe dentro de un plugin.
4. **Reescribe `dev-substrate:x` a `x`**: las skills de un proyecto no llevan namespace.
5. Baja las skills de terceros permitidas **desde su repo de origen, fijadas por SHA** en
   un manifiesto `terceros.json`, y copia cada una con su `LICENSE`. **Nunca pasan por el
   repo de `proyecto-loop`**, que es público.

Escribe la versión del loop en `.claude/loop/VERSION` y la lista de atribuciones en
`.claude/loop/TERCEROS.md`.

### Árbol resultante en un proyecto

| Ruta | Contenido | ¿Carga sola? |
|---|---|---|
| `.claude/skills/` | Skills del loop y de `dev-substrate`, más las dos de terceros | Sí |
| `.claude/agents/` | Subagentes de `dev-substrate` | Sí |
| `.claude/loop/` | Plantillas, referencias, catálogo de reglas, `VERSION`, `TERCEROS.md`, `dependencias-externas.md` | **No**, a propósito |
| `.claude/rules/` | Solo las reglas que instala `loop-rules` para el stack del proyecto | Sí |

El catálogo de reglas va a `.claude/loop/` y no a `.claude/rules/`: todo lo que está en
`.claude/rules/` carga automáticamente, y el catálogo completo no corresponde a ningún
proyecto en particular.

### Sincronización de la plantilla

Una Action en `proyecto-loop`, disparada por tags `v*`, corre `vendorear.py` y pushea el
resultado al repo plantilla. Necesita un token con permiso de escritura **solo sobre el
repo plantilla**, guardado como secret.

### `loop-actualizar` — skill nueva

Punto de entrada manual (`disable-model-invocation: true`), como `loop-ship`. Lee
`.claude/loop/VERSION`, baja `proyecto-loop` en el tag pedido, corre `vendorear.py` y
commitea el cambio como una unidad. **Conserva lo propio del proyecto**: las reglas que ya
instaló `loop-rules` y las claves de `.claude/settings.json` que no pertenecen al loop.

### `project-init`

Ya no necesita instalar el loop: viene en la plantilla. Si detecta que **no** está
vendoreado, lo dice y sugiere crear el repo desde la plantilla o correr `loop-actualizar`.
Sigue preguntando mobile y hosting de Supabase, y arma el scaffold como hoy.

## Gate diferido: `pendiente-dispositivos`

Cuando `loop-verify` no puede correr dispositivos —sesión cloud o máquina sin SDK— y
`state.md` dice `mobile: si`:

1. Corre tests, typecheck y lint como siempre.
2. Si pasan, la tarea queda marcada **`[d]`** en `plan.md`: verde en código, sin verificar
   en dispositivos. **No es `[x]`.**
3. Anota la tarea y sus pantallas en `.loop/deuda-dispositivos.md`.

**`project-loop` no entra en `entrega` mientras quede un solo `[d]`.** Se detiene y
reporta cuántas tareas deben la matriz. La deuda se salda corriendo `loop-verify` en un
entorno con dispositivos —la máquina local hoy, EAS cuando exista B—, que convierte `[d]`
en `[x]`.

Detectar el entorno es responsabilidad de `loop-verify`. **El entorno solo cuenta como
completo si puede correr los cuatro dispositivos**: `emulator -list-avds` (Android) **y**
`xcrun simctl` (iOS) tienen que responder. Si falta cualquiera de las dos plataformas —por
ejemplo, una máquina Linux con SDK de Android—, la tarea queda en `[d]`: verificar la mitad
de la matriz no es verificarla.

## Degradación explícita de skills ausentes

`.claude/loop/references/dependencias-externas.md` lista cada skill externa, qué etapa la usa y
**qué verifica**. Si una etapa la necesita y no está disponible, registra en
`review-log.md`:

> `NO VERIFICADO — design:design-critique no disponible en este entorno. Quedó sin evaluar:
> jerarquía visual (UI-007) de la pantalla H-03.`

Nunca se marca como aprobada una revisión que no corrió. Estas líneas no bloquean la
entrega, pero `project-loop` las lista en el reporte de entrega.

## El flujo, de punta a punta

1. **Una sola vez:** configurar el entorno cloud. La red *Trusted* alcanza para A. El setup
   script instala el CLI de Supabase.
2. **Una sola vez:** revisar si `engineering`, `design` y `figma` se pueden activar en la
   cuenta de claude.ai. Lo que se active ahí deja de estar degradado en la nube.
3. **Cada proyecto:** "Use this template" → sesión cloud sobre el repo → `/project-loop`.
4. `project-init` pregunta mobile y hosting, arma el scaffold, commitea y pushea.
5. En el checkpoint de diseño se revisa Figma desde cualquier dispositivo.

**Sigue necesitando la máquina local, hasta B y C:** saldar la deuda de dispositivos,
desplegar con `loop-ship`, y renderizar el video de `loop-pitch`.

## Supabase

**Desarrollo y tests en la nube no cuestan nada en Supabase.** El entorno cloud trae
Docker, así que Supabase puede correr dentro de la sesión con `supabase start`.

**La decisión de hosting de producción no cambia.** Correr el loop en la nube no obliga a
Supabase Cloud: el self-hosted sigue siendo válido, y las migraciones a producción las
aplicaría el runner del subproyecto C.

Para quien elija Supabase Cloud, precios consultados el 2026-09-23:

| Plan | Costo | Límite relevante |
|---|---|---|
| Free | USD 0 | 2 proyectos activos; **se pausa tras una semana sin actividad**. No sirve para producción |
| Pro | USD 25/mes por organización | Incluye una instancia Micro; **cada proyecto adicional suma ~USD 10/mes** |

## Verificación

**Chequeos automáticos sobre la salida de `vendorear.py`:** cero apariciones de
`${CLAUDE_PLUGIN_ROOT}`; cero namespaces `dev-substrate:`; toda ruta `.claude/loop/…`
citada existe; cada skill de terceros trae su `LICENSE`; `VERSION` coincide con
`plugin.json`.

**La prueba que cuenta:** crear un repo desde la plantilla, abrir una sesión cloud real, y
comprobar que las skills cargan, que `project-init` arma el proyecto y que `loop-verify`
marca `[d]` en una tarea de UI. **Sin esa corrida, A no está terminado.**

## Supuestos sin verificar

Se declaran para que la implementación los pruebe en vez de darlos por buenos:

- Que una sesión cloud pueda **clonar el repo público** `proyecto-loop` además del propio
  (lo necesita `loop-actualizar`).
- Que la red de la sesión deje **bajar las imágenes de Docker de Supabase**.
- Que desactivar el plugin global desde el `.claude/settings.json` del proyecto funcione
  como se espera en la máquina local.
- Que las skills de proyecto respeten `disable-model-invocation` igual que las de plugin
  (los puntos de entrada dependen de eso).
- Que una sesión que espera en el checkpoint de diseño sobreviva a la **expiración por
  inactividad**. La doc dice que al reabrirla se restaura la conversación, pero no el
  trabajo en segundo plano.
- Que `engineering`, `design` y `figma` se puedan activar en la cuenta de claude.ai.

## Riesgos

- **La calidad de revisión en la nube es menor** hasta que se activen las skills oficiales
  en claude.ai. La degradación explícita lo hace visible, pero no lo resuelve.
- **La deuda de dispositivos puede acumularse.** Un bug de forma en tablet se descubre
  varias pantallas después. Es el costo aceptado del gate diferido, y lo cierra B.
- **Cada proyecto pesa ~6,5 MB más** por las skills de terceros, y cada actualización suma
  a la historia de git.
- **Deriva de versiones.** Los proyectos no se actualizan solos; un proyecto viejo puede
  correr un loop viejo. `VERSION` lo hace visible y `loop-actualizar` lo resuelve, pero
  hay que correrlo.

## Fuera de alcance

- La matriz de dispositivos en EAS (subproyecto B).
- El deploy con runner self-hosted (subproyecto C).
- Vendorear skills sin licencia o las oficiales de la app.
- Cambiar la decisión de hosting de Supabase de ningún proyecto.
